# Human production KMS provider

`layerx-human-kms` hosts LXKP over mandatory mutual TLS. The configured client leaf certificate is pinned in addition to CA verification. It stores Ed25519 keys in an AES-256-GCM encrypted, atomically replaced and synced snapshot, with a process lock, private directory/files and durable destruction tombstones. There is no private-key export operation. This is a sealed software provider, not an external hardware KMS certification.

Required environment variables use `LAYERX_HUMAN_KMS_`: `LISTEN`, `STATE_DIR`, `PROVIDER_REFERENCE`, `DEADLINE_SECONDS` (1–60), `REGISTRY_FILE`, `CLIENT_CA_DER`, `CLIENT_CERT_DER`, `TLS_CERT_DER`, `TLS_KEY_DER`, and `SEAL_SECRET_FILE`. File paths must be absolute, regular files owned by the provider UID; keys and the 32-byte random seal secret must have no group/other permissions. Registry and certificate files must not be group/other writable. Protect the seal separately from the state volume. The registry JSON is an operator-protected snapshot of the actual core handshake: `network_id`, `protocol_version`, and `modules` containing numeric `module_id` and `activity_types`. This executable does not provision or fabricate that handshake evidence.

Requests are bounded four-byte-length-prefixed LXKP frames. Version 1 probe/create/describe/destroy/sign retain their existing encoding. Version 1 rotate is explicitly refused. Version 2 is accepted only for rotate (operation 3): append the expected current 32-byte public key after the existing binding/network/class/reference fields. The response retains the existing description and stable opaque reference, with version 2 in its header.

Rotation commits the new key and immediately previous public key together before replying. A retry naming that immediately previous key returns the exact committed description, including after restart. A deliberate next rotation names the current key. Older or conflicting expectations return typed Conflict. Create retries are idempotent before any rotation; a create against a rotated or destroyed identity conflicts. Repeated destroy succeeds; tombstones prevent recreation.

The authenticated Human service is the principal authority: LXKP carries its digest binding, network and key class, not raw principal credentials. The provider enforces exact binding/reference/class on every operation. It independently decodes canonical activity bytes under the protected registry and network/protocol, reconstructs the disclosure and verifies the signing digest. Human authorization, step-up and account policy remain in the real caller; this service does not invent an independent end-user authorization API.

LXKP version 3 adds operations 6 (resolve EVM wallet), 7 (register an exact authorized plan and reserve its nonce), 8 (sign the registered action), 9 (acknowledge the exact transaction hash), and 10 (recover the action journal). Operations 7–10 append a length-prefixed strict JSON payload. Version 3 does not accept legacy opcodes. The existing service client pin alone can authorize plans. Optional `LAYERX_HUMAN_KMS_EVM_CLIENT_CERT_DER` pins a separate movement executor certificate, authenticated by the same client CA, permitted only operations 6, 8–10 and 12. That executor cannot create, rotate, destroy, authorize or use the legacy signer.

EVM authorization binds the principal and tenant names, custody binding, wallet, plan and stable action key, validity window, and every EIP-1559 field. Nonces are durably reserved per wallet and chain before returning authorization. Conflicting actions cannot reuse or regress a reserved nonce; exact retries return the original entry. Signing returns canonical type-2 RLP transaction bytes and their Keccak hash, never secp256k1 private material. Signed transactions are durably journaled before returning and can be recovered and resubmitted after an acknowledgement gap. Acknowledgements require the exact journaled hash. Custody destruction removes the EVM key and action journal along with the primary signing key.

Version 3 operation 11 signs an owner SEND authorization for a service-authorized movement plan. It accepts typed source/destination/asset, amount, sequence, idempotency, context, expiry, network/protocol and principal custody scope. The KMS constructs the native `lxp_send_authorization_message` byte layout and signature domain itself; there is no arbitrary-message or arbitrary-digest signing endpoint. Its action key, exact request and signature are persisted before returning. Conflicting retries refuse. Only the human-service certificate may invoke this operation; the movement executor cannot.

Version 3 operation 12 accepts an externally supplied 65-byte EVM signature for an already service-authorized action. Both pinned clients may invoke it. It checks the exact EIP-1559 preimage, low-s encoding and recovered bound wallet, accepting parity 0/1 or 27/28. It stores the resulting raw transaction and hash in the same durable acknowledgement journal. Expired or unknown actions, wrong wallets and changed signed transactions refuse; identical retries recover the recorded action.
